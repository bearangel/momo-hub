# M3.0 收官清理与协议前置 — 设计规格

- **状态**：已定稿（三路探查结论已回填：协议握手全图 / keychain 调用面 / CI 失败 artifacts 实锤）
- **日期**：2026-10-28
- **上游**：`docs/specs/2026-10-28-momo-hub-m3-roadmap.md` §2.1（已批准，用户全系列预授权）
- **定位**：M3 首期。无新功能面，6 张票：1 项协议前置 + 5 项债务清偿。完成即冻结，开 M3.1。

## 1. 目标与非目标

**目标**

1. 协议兼容前置：让后续 M3.1/M3.2 的新 RPC 对旧节点**显式降级**（可读错误 + 版本可见），而非静默 `unknown_method`。
2. 清偿 M2 系列遗留的 5 项已定案债务（0-2/0-3/0-4/0-5/0-7）。

**非目标（明确不做）**

- 0-6 readonly 持久化（维持 M2.5「设计边界」裁决，已批准不纳入）。
- 协议版本号提升到 1.3.0（留给 M3.1 实际新增方法时一并提）。
- hub 默认端口变更（8787 不动；`*:18787` 是验收期绑定，非产品行为）。
- 任何 M3.1+ 的功能实现。

## 2. 事实基线

### 2.1 T1 · 协议版本协商现状（探查定案）

**包结构（关键事实）**：
- hub 仓**根包即 `momo-hub-protocol`**（`src/version.ts` 是唯一常量源）；`packages/hub` 经 `link:../..` 消费，hub 仓内部零重复。
- studio 侧源码**无常量副本**——`electron/src/main/hub/protocol.ts` 是 2 行 barrel `export * from 'momo-hub-protocol'`；实际冻结副本在 pnpm store（`electron/package.json:102` pin `github:bearangel/momo-hub#v0.1.5` = commit ffd36e1，dist-only tarball）。当前两侧值同为 `'1.2.0'`（pin 恰好够新，纯属巧合）。

**版本闸门全表**：
- `src/version.ts:4` PROTOCOL_VERSION='1.2.0'；`:6-16` `majorOf` + `isCompatible` **只比 major**。
- **唯一运行时检查点**：hub `packages/hub/src/server.ts:178-184`（hello 闸门）。`protoVer` 缺失按 `''` 处理 → `majorOf('')`=null → 拒收。
- **studio 从不检查 hub 版本**：`HelloRes.protoVer` 已在响应中（`server.ts:193`），但 `client.ts:201-212` ok 分支只读 `onlineNodes`，protoVer 被完全忽略；`electron/src` 下零 `isCompatible` 引用。
- 测试模拟偏差：`m2-integration.test.ts:260-262` 模拟 hub 用**严格相等**，比真实 hub（major-only）更严。

**握手链路**：`POST /enroll`（无版本参与）→ `GET /ws` Bearer token（4401）→ hello（超时 4403，5s 双侧定时器）→ req `{protoVer, nodeName?}` / res `{hubId, protoVer, serverTime, onlineNodes}`（`src/methods.ts:26-28`）→ 失败 `{code:'proto_version_mismatch', message:"hub=1.2.0 node=<ver>"}` + `close(4402)`。

**错误链路断点（设计必须修的）**：`RpcErrorPayload.code` 在 `client.ts:195`（pending RPC reject）与 `:217`（hello 拒绝）**两处被丢弃**，只有 message 字符串存活到 store/UI。版本不兼容时 studio **无限退避重连**（`client.ts:148-157`，无终态概念，状态机仅 `'disconnected'|'connecting'|'online'`），UI 只显示裸 lastError 文本 + 「自动重连中」。

**分发层**：hub RPC 表 `server.ts:95-110`（RPC_HANDLERS），未命中 → `errPayload('unknown_method', env.method)` `:211`（message 就是方法名，无人类文案）；studio 节点侧应答器 `hub/index.ts:356`（`节点不支持的方法: <method>`）+ `view-server.ts:200-201`。

**测试覆盖**：hub `protocol-m2.test.ts:47-56`（常量+isCompatible 矩阵）、`server.integration.test.ts:118-133`（真 WS 版本不匹配→4402）、`:135-146`（unknown_method/4400）、`:205-214`（4403）；studio `client.test.ts:43-51,186,201-203,253`（hello 拒绝→退避重连、拒绝后不发快照）、`protocol-pin.test.ts:48-51`（pin 锁 0.1.5）。**缺口**：零 minor 偏斜用例、零 protoVer 消费用例、零 code 传播用例。

### 2.6 T6 · CI e2e 隔离现状（探查定案——已拿到失败实锤）

证据源：PR #1 round-2 失败 run `40676120418` 的 GitHub Actions artifacts（error-context.md + 截图 + trace.zip，已下载至 `/var/folders/g0/0vb8n78d4v18wstl_tk1gsw40000gn/T/opencode/e2e-artifacts/`，2026-11-04 过期）。

**共同根因（单一事实，两种机制）**：GitHub `macos-latest` runner 显示器 **1024×768，最大化 workarea ≈ 1024×677**（截图实测）。两条 spec 都假设了开发者尺寸的显示器。

- **kanban-drag 失败于 `:104`**（卡未落入已关闭列）：看板需 ~1530px 内容宽（5×232px `w-[232px] shrink-0`（`BoardColumn.tsx:100`）+ 间距 + 活动栏/侧栏 ~300px）>> 1024 视口。已关闭列 `boundingBox()` 中心 x 在视口外，`mouse.move` 派发进死区 → dnd-kit `over=null`（live-region 实证 `Draggable item T-001 was dropped` 且卡仍待办、泳道已横向滚动=自动滚动部分启动但 20 步 CDP 事件毫秒级完成追不上 rAF 节奏）。**非焦点/权限/时序问题，纯指针可达性几何**。

- 本机全绿原因：开发机显示器足够宽/高，目标中心在视口内、增高余量充足。
- `retries: CI?2:0` 无效：几何确定性失败，非 flake。

## 3. 票据设计

### 3.1 T1 · 协议能力协商 / 最低 minor 门槛（设计定稿）

**设计原则**（momo-boundary-rules）：新增字段/方法，不改既有字段语义；两端同 commit；契约测试锁形状。

**语义分层**：`PROTOCOL_VERSION = major.minor.patch`
- major 不匹配 = 不兼容（现状保留，hello 闸门拒绝）。
- **minor = 向后兼容的新增**（新方法、新可选字段）。接收端遇未知可选字段忽略（现状已如此）。
- 「能力门槛」= per-feature 的 `requiredMinor`，不做全局 caps 数组（caps 需维护全集，易漂移；minor 分层复用版本号天然有序）。

**hub 侧（hub 仓）四件**：

1. **协议包**（`src/version.ts` / `src/methods.ts` / `src/error.ts`）：
   - 新增 `protocolSupports(peerVersion: string, requiredMinor: number): boolean`（major 相等且 peer minor ≥ requiredMinor；非法串 false）。
   - 新增 `METHOD_REQUIRED_MINOR: Record<string, number>` 方法表——M3.0 全量登记为 `2`（1.2 基线），M3.1/M3.2 增量登记；未登记者视为基线 2。
   - `RpcErrorCode` 联合新增 `'unsupported_method'`（与既有 `'unknown_method'` 并存：表内但 minor 不够 = unsupported；不在 RPC 表 = unknown，语义不漂移）。
   - `RpcErrorPayload` 新增**可选**字段 `method?: string` / `requiredMinor?: number`（接收端忽略未知字段，向后兼容）。
2. **server 分发守卫**（`packages/hub/src/server.ts:95-110,204-213`）：hello 闸门通过后把连接的 `protoVer` 存入 per-socket 状态（内存，不做 DB 迁移）；分发时若 `METHOD_REQUIRED_MINOR[method] > minorOf(socket.protoVer)` → 返回 `unsupported_method` + `{method, requiredMinor}` 结构化载荷（message 用人类文案含双方版本）；未入 RPC 表 → 维持 `unknown_method` 现状。**M3.0 全表=2，守卫永不触发，对 1.2 节点逐字节等价**。
3. **版本可见**：HelloRes 已带 `protoVer`（现状，无需改）；hub 无需额外端点。
4. **契约测试**：minor 偏斜三态（peer 1.1 调 minor-2 方法 → unsupported_method 结构化；peer 1.2 → 正常；1.9 → 正常）+ 既有错误形状锁 + `protocolSupports` 矩阵。

**studio 侧（studio 仓，随 pin 升级到 hub v0.1.6）四件**：

1. **pin bump**：`electron/package.json:102` → `github:bearangel/momo-hub#v0.1.6`；`protocol-pin.test.ts:48-51` 同 commit 更新为 0.1.6。
2. **版本管道**：`client.ts:201-212` hello ok 分支读取并保存 `HelloRes.protoVer`；`HubStatus` 新增 `hubProtoVer: string | null`；`hub:stateChanged` 载荷带上（IPC 类型两侧同步改 + 双 typecheck）。
3. **错误 code 传播**：`client.ts:195/:217` 两处不再丢 code——pending RPC reject 改用带 `code` 的错误类型（`Error` 子类，`readonly code: string`，message 原样保留零行为变化）；hello 拒绝时 `lastError` 之外新增 `lastErrorCode: string | null` 进状态广播与 `HubStatus`。
4. **诊断显示**：HubSettingsPanel 状态行显示 `hub 协议版本 <hubProtoVer>`；`lastErrorCode === 'proto_version_mismatch'` 时错误行追加固定文案「hub 协议版本不兼容，请升级 hub 或客户端」。（文案级小改，非布局变更。）

**测试对齐**：`m2-integration.test.ts:260-262` 模拟 hub 的严格相等改为与真实 hub 一致的 major-only + HelloRes 带 protoVer；studio 侧新增 code 传播用例（hello 拒绝 → lastErrorCode 进 store；RPC 拒绝 → err.code 可读）。

**兼容矩阵（验收口径，不变）**：

| 场景 | 期望 |
|---|---|
| 1.2 node ↔ 1.2 hub | 全现状行为，零变化（守卫全表=2 永不触发） |
| 旧 studio（pin<1.3）→ 新 hub 调 1.3 方法 | `unsupported_method` + `{method, requiredMinor}`，可读降级 |
| 新 studio → 旧 hub 调 1.3 方法 | 旧 hub 返回 `unknown_method`（方法不在其表）；studio 侧 M3.1 起用 `hubProtoVer` 预判给版本提示（本票只铺管道） |
| major 不匹配 | 现状拒绝行为不变；studio 侧新增 mismatch 专属文案（经 lastErrorCode） |

### 3.5 T5 · keychain 服务名作用域化（设计定稿）

**单一作用域点（统一到 keychain.ts 门面）**：

**测试**：门面作用域双态（默认=裸服务名；两个隔离目录=两个不同服务名、互不可见）+ 五族键写入走分域服务名 + D2 用例迁移后等价。注入惯例 `setKeychainImpl` 不变。

### 3.6 T6 · CI e2e 解禁（设计定稿——按 artifacts 实锤适配）

**先造本地复现几何**：spec 内支持 `E2E_PIN_GEOMETRY=1024x677`（dev-only env，经 `app.evaluate` + `setContentBounds` 在 firstWindow 后钉死窗口）——把「CI 必红」变成「本机可复现」，适配验证零 CI 往返。

**kanban-drag 适配（A1：拖拽中程序化滚动泳道）**——保留完整 PointerSensor 链路，只修指针可达性：
```
down 卡片 → move +12px（过 5px 激活阈值，BoardCanvas.tsx:55）
→ win.evaluate 把泳道容器 scrollLeft 滚到底（Lane.tsx:73 overflow-x-auto）
→ 重取已关闭列 boundingBox（滚动后新坐标）
→ move 到目标中心（steps: 8）→ up
```
前置验证点：dnd-kit DndContext 拖拽期间跟踪祖先滚动偏移（droppable rect 随滚动更新）——钉几何本地跑即为验证。备选 A2（边缘驻留等自动滚动带回目标，最像真人但节奏不稳）/ A3（KeyboardSensor：Space+ArrowRight+Space，`BoardCanvas.tsx:248` 已配置，同一 onDragEnd/move-IPC 链）。A1 验证不过则按 A3 兜底。

**browser.spec 适配（B1：增高腿 → 收缩腿）**——收缩永不被 AppKit 钳制：
```
settle 腿不动（1100×700，CI 钳到 677 后 view 高度 ≈547 仍在 (400,620) 收敛窗内，已验证两侧皆绿）
增高腿改为 setContentBounds(height: 600)（window.ts:27 minHeight）
断言 delta <= -50（CI：677→600≈-77；本机：700→600=-100）
x 不位移 / 宽度不变两条断言（:416-417）原样保留
```
生产链路不变（window resize → ResizeObserver → browser:setSidebarBounds → view.setBounds），只是方向翻转。

**收尾三件**：删 `playwright.config.ts:31-33` testIgnore 分支；修正 config 注释 `:27-30` 与 `CHANGELOG.md:17` 的失实归因（「拖拽时序/多窗口」→「runner 显示几何 1024×768：指针可达性 + workarea 钳制」）；retries 维持现状（几何确定性失败已修，retries 不再背锅）。

**解禁判据**：钉几何本地全绿 → PR CI（无 testIgnore）三连绿 → 才算 T6 完成；CI 仍红即回滚该票，不裹挟其余票。

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| T1 动分发层伤既有 RPC | 方法表 M3.0 只登记 1.2 基线（全部 minor=2），分发行为对 1.2 节点逐字节等价；契约测试锁既有错误形状 |

| T6 适配改动引入本地回归 | 本地全量 e2e + CI 三连绿才删 testIgnore；失败即回滚该票（其余票不裹挟） |
| 过夜自主无人裁决 | 用户级决策已预授权定格；技术争议以 Momus/oracle 结论为准；无法收敛时该票回滚不阻塞其余票 |
